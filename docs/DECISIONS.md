- **D-031 ALDI API facts (unofficial; adapter `services/scraper/src/aldi-client.ts`).** Host `https://api.aldi.com.au`. Category tree: `GET /v2/product-category-tree?currency=AUD` (adding `serviceType` returns 400 code 3801). Products: `GET /v3/product-search?currency=AUD&serviceType=walk-in&servicePoint=G526&categoryKey=<key>&q=<text>&limit=<n>&offset=<n>`; `limit` must be one of 12, 16, 24, 30, 32, 48 or 60 (else 400 code 3731); paging is `offset` with `meta.pagination.totalCount`; deep offsets work (3,240 of 3,292 tested). Product fields used: `sku` (18-digit string, kept verbatim), `name`, `brandName` (upper case; display-cased), `sellingSize` ("2 l", "1 each", "approx. 0.96 kg per package", null for loose and some liquor), `weightType` ("0" fixed, "1" random-weight pre-pack, "3" loose by weight), `quantityUnit` (ea/kg/bt/pac), `price.amount` (cents), `price.comparisonDisplay` ("$1.70 per 1 L"), `price.perUnitDisplay` ("1 kg" for loose), `categories[]` (id, name, slug path; top level then leaf, for every tree the product is in), `assets[].url` (template, see D-033). Every product reports `notForSale: true` (ALDI AU has no online shop), so it is ignored; there is no stock/availability field. **Bot protection:** Akamai returned 403 "Access Denied" HTML to a Chrome-like User-Agent from a non-browser client but 200 to a plain client UA; we send an honest UA `TrolleyCatalogue/1.0 (personal household shopping list)` with no contact details, never a browser UA. Whether AWS IP ranges are blocked can only be confirmed after deploy (A15).
- **D-032 Crawl strategy and sizing.** Crawl every top-level category of the tree (including promotional trees such as Christmas, which hold seasonal items found nowhere else) with page size 60, deduping by SKU; plus one unfiltered request for the expected total (coverage check in the run record). About 75 requests at >= 1 s apart (configurable, never below 0.5 s), max 3 attempts per request with exponential backoff and Retry-After, 20 s timeout, a hard budget of 400 requests, a 10,000-product cap, 50 pages per category, and a deadline 2 minutes before the Lambda timeout. Estimate: ~2-3 minutes and < 100 MB for the full ~3,300 products, so 15 minutes / 512 MB is ample headroom (A10). A 403 or HTML response stops the crawl immediately (retrying a bot block makes it worse).
- **D-033 Product images are hotlinked** from ALDI's CDN `https://dm.apac.cms.aldi.cx/is/image/aldiprodapac/product/jpg/scaleWidth/{width}/<uuid>/{slug}`: we store the front-of-pack (`FR01`) asset at width 400 (2 columns at ~180 CSS px on 2x screens). Only `https://*.aldi.cx/` URLs are accepted. The CSP `img-src 'self' data: https:` already allows it; nothing is copied to S3. The CDN host was not reachable from the build session (egress proxy), so loading on phones is a post-deploy check (D9).
- **D-034 Search runs in memory in the API Lambda.** Every catalogue item carries `gsi1pk = CATALOGUE#PRODUCT`, `gsi1sk = <groupId>#<sku>`; one paginated GSI1 Query (with a projection of the fields search needs, ~2 MB, 2-3 pages) loads the catalogue into a per-container cache with a 10-minute TTL; concurrent requests share one load and a failed refresh keeps serving the stale copy. Chosen over a snapshot item (400 KB item limit would need chunking and a second write path to keep in sync) and over an S3 snapshot (extra bucket, scraper write grant and staleness handling) for one source of truth and no new resources; cost is ~500 read units per container per 10 minutes, fractions of a cent. Household custom products (`HH#<hh>` / `PRODUCT#custom-<uuid>`) are queried per household with a 60 s cache (a create updates the local cache; the other phone sees it within a minute) and merged into results. Ranking (`packages/core/src/search.ts`): every query token must match a name/brand word as exact, light-stemmed (banana/bananas) or word prefix; exact > prefix; name > brand; bonus when the token is the name's head noun (last non-size word, so "milk" ranks Light Milk 2L above Milk Chocolate Block); custom products +0.25; ties by name then SKU. `ProductDeps.historyBoost(householdId)` is the hook for purchase history (Stage 3). Measured well under 10 ms per query over 3,000 products (C9). Default page size 20, max 48, opaque offset cursor; responses include `total`.
- **D-035 Monthly schedule and alerting.** EventBridge Scheduler `cron(0 3 1 * ? *)` in `Australia/Sydney` invokes `trolley-scraper` with no Scheduler retries and no Lambda async retries (a failure should alert, not hammer ALDI). Any failed or aborted run throws, so the alarm `trolley-scraper-errors` (Lambda Errors >= 1 in 5 minutes) emails `ALERT_EMAIL` via SNS. Unlike the budget, the SNS email subscription must be **confirmed** by clicking the link AWS sends after the first deploy. Alarm and topic are only created when `alertEmail` is set (it always is for deploys).
- **D-036 "Scrape now" uses the deploy role, narrowly.** `.github/workflows/scrape.yml` (workflow_dispatch, main only) invokes the Lambda synchronously and fails if it returns a FunctionError. The OIDC deploy role gains exactly `lambda:InvokeFunction` on `arn:aws:lambda:ap-southeast-2:<account>:function:trolley-scraper` (fixed function name). Because `TrolleyGithubOidcStack` is deployed by hand, the user must re-deploy it once from CloudShell (docs/SETUP.md step 2c) before the workflow works.
- **D-037 GitHub-runner fallback is opt-in, with its own role.** `.github/workflows/scrape-fallback.yml` runs the same CLI on a runner (dry run by default; a monthly schedule that does nothing unless repository variable `SCRAPE_FALLBACK_ENABLED=true`). Writing to DynamoDB from GitHub would give a CI identity data-plane access to production, so it is **not created by default**: deploying `TrolleyGithubOidcStack` with `-c scrapeFallbackTableName=<TableName>` creates a separate role `trolley-github-scrape-fallback` (main branch only) that can Query GSI1, Query `SCRAPE#*` and BatchWrite/Put only items whose partition key starts `PRODUCT#` or `SCRAPE#` (IAM `dynamodb:LeadingKeys`), never household data. The deploy role is unchanged by this.
- **D-038 Scraper and data rules.** Scraper Lambda role (and the fallback role): Query on GSI1, Query on `SCRAPE#*`, BatchWriteItem/PutItem restricted to `PRODUCT#*`/`SCRAPE#*` partition keys; no Delete/Update/Scan, no `*` (narrower than A14). Products are `PRODUCT#<sku>` / `META` with `firstSeenAt`, `lastSeenAt`, `missedRuns`, `discontinued`, `discontinuedAt`; never deleted. Run records `SCRAPE#RUN` / `<startedAt ISO>` with status `succeeded` | `failed` | `aborted` and counts (fetched, new, updated, unchanged, reactivated, missed, discontinued, errors), store, baseline, unitType distribution and unmapped categories. **Aborted** (A8): fetched < 50% of the last *succeeded* run's count (falls back to the active product count if run records are missing; first run exempt) -> no product writes at all. **Failed**: crawl incomplete (block mid-way, error, deadline) or empty -> freshly seen products are still upserted (they are real data) but nothing is counted as missed or discontinued. Only succeeded runs advance `missedRuns`; 2 consecutive misses -> discontinued. BatchWrite chunks of 25 with UnprocessedItems retry and exponential backoff (8 attempts, then the run fails).
- **D-039 Default unitType and groups.** Loose items (ALDI `weightType` 3, "per kg") -> `kg`; random-weight pre-packs ("approx. 0.96 kg per package", e.g. steaks, mince "per kg") -> `pack` with pack size "approx. 0.96 kg", because you pick up packs, not kilos; "1 each" -> `each`; "N each" or "N pack" -> `pack`; fixed weights/volumes ("2 l", "500 g") -> `pack` (spec example); "per 100 g" -> `g`; "per litre" -> `L`; nothing recognisable -> `each`. ALDI's own range has no `g`/`L`/`mL` products, so those types come from custom products and user overrides. Live sample of 223 Casey products: pack 205, each 11, kg 7. ALDI categories map by leaf key, then top-level key (promotional trees never win), then slug, then category-name keyword, then promotional leaf (Christmas > Chocolate -> Snacks), then product-name keyword, else Other (reported in the run record). Deli is its own group (ALDI has a Deli & Chilled Meats aisle); Pantry > Confectionery/Chips/Biscuits/Crackers/Nuts -> Snacks.
- **D-040 API shape notes for Stage 1.** Items use `groupId` (criterion C1 says "group"; same meaning, id of a group from `GET /api/groups`). `POST /api/products/custom` accepts optional `brand`, `packSize`, `unitType` (default each) and `groupId` (default other) and **allows duplicate names** (docs/ux/search.md offers "Use existing" instead of blocking); max 500 custom products per household.

## Stage 2 decisions (2026-11-22, PM)
- **D-046 Merge rule.** Adding a product (from search, template or list creation) to a list or template that already has the same product with the same unit sums the quantity; a different unit is a separate row. Notes: kept if equal, otherwise joined with " / ". On lists the sum is an atomic update so two phones adding the same product never lose one.
- **D-047 Items carry a product snapshot** (name, brand, image URL, pack size, groupId, unitType) taken when added. Lists, templates and history render without the catalogue and survive discontinued products. Group is the snapshot's group; catalogue regrouping does not move items already added.
- **D-048 "This week" list.** Zero or one active list is flagged; flagging is one atomic write; the first list is flagged automatically; archiving clears the flag (not reassigned). Add-from-search targets it by default, and if none exists confirm creates a blank "Week of <Monday>" list and flags it (same rule MCP `add_item` will use in Stage 4).
- **D-049 Auto-archive is server-side and immediate, with Undo** rather than a "Archive?" prompt: the tick that completes a list archives it via a conditional update (exactly once under races) and the client shows an 8 s Undo. Undo returns the list to active with items still ticked; it re-archives only on a later completing tick. "Finish shop" archives with unticked items (out-of-stock is normal at ALDI); those are recorded as not bought.
- **D-050 Purchase rows** written on archive, one per ticked item: `HH#<hh>` / `PURCHASE#<productId>#<completedAt date>#<listId>` with qty, unit, listId, completedAt. The listId suffix (beyond spec 5.1) avoids collisions when two lists are completed the same day; keys are deterministic so re-archiving is idempotent. Undo deletes them. Custom products use their custom id. Feeds Stage 3.
- **D-051 Stage 2 cuts.** Offline queueing, category-mapping editing, group rename/add, save list as template, copy an archived list, deleting archived lists moved to backlog (B-006 to B-011). Sync stays polling (10 s in shop mode, refetch on focus); per-row atomic updates plus version checks on edits (409 -> refetch) instead of websockets.

## Stage 2 backend (2026-11-22, senior engineer)
- **D-052 Quantity rule for stored lines (A2 interpretation).** qty > 0; whole numbers for each/pack/g/mL; at most 2 decimal places for kg/L; max 999 (g and mL: 99,999). "A multiple of the unit's step" is read as the unit's precision, because the quantity modal's own presets and minimums are off-step (250 g preset vs 100 g step, 0.05 kg min, typed 1.3 kg, D-026/quantity-modal.md) and its 1000 g/mL presets exceed 999. A merge that would pass the max is a 400 on `qty` (bulk template adds cap at the max instead). Notes: <= 200 chars (the modal caps typing at 140).
- **D-053 Line ids are `<productId>~<unit>`.** List items (`ITEM#<productId>~<unit>`) and template items use the merge key as their id, so two phones adding the same product and unit meet on one row and merge (version-checked write, retried) instead of creating duplicates (C4). Changing an item's unit re-keys it in one transaction (merging into an existing row with that unit); responses carry `replacedItemId`. Adding more of a ticked item unticks it (more is needed).
- **D-054 Purchase row key amends D-050:** `PURCHASE#<productId>#<local date>#<listId>#<unit>`, so the same product in two units on one list gives two rows. The date is the household-local date (`Australia/Sydney`) of `completedAt`. Rows: productId, name, groupId, qty, unit, listId, completedAt, date. Written after the list's conditional archive update (idempotent BatchWrite, not in the same transaction: a list can hold up to 200 items, past the 100-op transaction limit); Undo deletes them.
- **D-055 Undo window is 2 minutes server-side** (`POST /api/lists/{id}/reopen`; the UI toast is 8 s, the margin covers slow networks). Outside it History stays read-only (409 `UNDO_EXPIRED`). Reopen needs a free active-list slot (10 max).
- **D-056 "This week" is one pointer item** `HH#<hh>` / `THISWEEK` -> `listId`. Flagging is a single Put (with a ConditionCheck that the list is active), so "exactly zero or one" holds by construction. A list's `thisWeek` is derived: pointer matches and the list is active. Archiving therefore clears the flag without a second write, and Undo restores it if nothing else was flagged meanwhile. A new list is auto-flagged when no *active* list is flagged (conditional Put on the pointer); `POST /api/this-week/items` creating "Week of" at the same moment on two phones keeps one list (the loser deletes its empty list and uses the winner's).
- **D-057 GSI2 for household lists by status** (`gsi2pk = HH#<hh>#LISTS#active|archived`, `gsi2sk = createdAt|completedAt#id`, projection ALL, on demand - no fixed cost). Not GSI1, because the scraper and fallback roles may Query GSI1 and must never see household data. Active-list progress is computed from item queries (<= 10 lists) rather than counters on the list row, so ticks never contend on one hot row; archived lists store `itemCount`/`boughtCount`. GSI reads are eventually consistent: a list created a moment ago may be missing from `GET /api/lists` for up to a second (clients merge their own optimistic result).
- **D-058 Concurrency and 409s.** Every list-item write is a transaction: ConditionCheck "list is active" + one conditional write of that item's row (transaction conflicts retried with jitter), so archived lists reject writes (409 `LIST_ARCHIVED`) and nothing ever rewrites the whole list. Ticks are idempotent sets with no version; qty/unit/note edits and renames require the row's `version` (409 `STALE` with `current`). Auto-archive: after a tick the items are re-read (strongly consistent) and, if all are ticked, `active -> archived` is a conditional update, so it happens exactly once (the loser of a race gets `archived: false` with `list.status = 'archived'`). Known gap, accepted: an untick landing between that read and the archive update archives with the earlier snapshot. Templates embed items: adds retry on a template-version clash (no lost adds); item edits check the item `version`; renames check the template `version`. Aisle order PUT takes an optional `version` (0 = never saved). 409 body: `{ code: 'CONFLICT', reason: 'STALE'|'LIST_ARCHIVED'|'NOT_ARCHIVED'|'LIMIT'|'UNDO_EXPIRED', message, current? }`.
- **D-059 Mock API (VITE_MOCK_AUTH) mirrors Stage 2 with the same core rules** and persists to `localStorage` (`trolley.mock.stage2.v1`), re-read on each request, so reloads and two pages in one Playwright context share state (H4). Seed per household: flagged "Week of <Monday>" list (21 items across 11 groups, 6 ticked, notes, kg and a custom L item), "Weekly basics" (weekly, 10) and "Tacos" (meal, 5), two archived lists. Seams: `window.__mockApiFail = { match: 'PATCH /api/lists/', status: 500, times: 1 }`; `navigator.onLine === false` makes calls reject like the network.

## Stage 3 backend (2026-11-22, senior engineer)
- **D-069 Engine details** (`packages/core/src/suggestions.ts`). Count = distinct purchase dates (two lists on one day are one purchase). Average qty is per list, in the product's most-bought unit (ties: the latest); kg/g and L/mL convert, other units count as dates only. A due product is dropped as **lapsed** when days since last > max(4 x median, median + 42 days) (weekly items lapse after 7 weeks, monthly after 4 months), so things the household stopped buying do not top the list; template items never lapse. Cold start = fewer than 3 distinct `listId`s in the purchase rows (a list archived with nothing bought does not count). Weekly templates merge by D-046 (one line per product: the first unit wins); template items come first in aisle order then name, then due items by days since / median (ties: count, then name). Template-and-due reason: "On your weekly template - usually every ~7 days, last bought 6 days ago". History items are shown with a fresh catalogue/custom snapshot; one that no longer resolves is dropped. Known gap: discontinued catalogue products can still be suggested (they can still be added).

- **D-080 Store-specific catalogue: `notAtStore` (Stage 2b E1/E2).** Investigated live on 22 Nov 2026 (about 130 polite requests; plain client UA, since the honest UA was 403'd from this host's IP). Findings: (1) The product payload has **no per-store stock or availability field**: `notForSale` is true for all, `notForSaleReason`, `discontinued`, `isDropship`, `isAbstract`, `countryExtensions` and `badges` are constant across all 3,294 Casey products. (2) `servicePoint` changes **range membership only**, and only slightly: Casey 3,294 SKUs, Gungahlin G662 3,360 (173 Casey-only, 239 Gungahlin-only, mostly Special Buys and a few pantry lines), no store 3,285. Fields for shared SKUs are identical (price differed on 2). So Casey's scrape is already Casey's range as ALDI defines it; the surplus is not a mismatch of store id. (3) Two real signals identify products the store will not have on the shelf: (a) **`onSaleDate`** (Special Buys, "While Stocks Last" or "On Sale Wed 02 Dec"): 266 of the Casey products have a date in the future, i.e. announced but not in store yet (136 Christmas, 95 uncategorised, rest Pantry/Drinks/Liquor); 426 more have past dates (in store now or already sold out; unknowable). (b) **The store's liquor licence**: `GET /v2/service-points/G526` returns `alcoholAvailability: ["Beer","Wine"]` (443 of 567 stores say Beer+Wine, 173 none, 1 Beer only; no store lists Spirits). The liquor range is NOT filtered by it (a Beer-only store still gets wine and spirits), so Casey's catalogue holds about 31 spirits, liqueurs and spirit premixes (Whisky, Gin, Vodka and Cola, Irish Cream) that the store cannot sell. Many sit outside the Liquor tree (no categories, or Christmas), so category exclusion is not enough; `ageRestriction: 18` marks all 133 alcohol products. Category keys, `q`, `categoryKey` and `serviceType` give no further signal (`serviceType` on the tree is a 400).
  **Decision (E2, mark not delete):** the scraper sets `notAtStore: true` (plus `onSaleDate` when given) on (a) products whose `onSaleDate` is after today in Australia/Sydney, and (b) products classified as spirits (`packages/core/src/alcohol.ts`: category Spirits; category Premixed unless beer/cider/ginger-beer based; or age-restricted with a spirit word in the name such as gin, vodka, whisky, bourbon, rum, tequila, liqueur, cola mixes) when the store's `alcoholAvailability` lacks Spirits (one extra `GET /v2/service-points/<id>` per run; if it fails nothing is flagged for licence). Beer, wine, cider and anything ambiguous (for example an uncategorised "Premium Cuvee") are kept: we never hide what we are unsure about. Flagged products are written like any other (never deleted, still discontinued-tracked, still readable by SKU) and `searchProducts` skips them unless `includeNotAtStore`. The date flag **lapses by itself**: search treats `notAtStore` as false once `onSaleDate <= today` (`isNotAtStore`, `storeToday`), so a Special Buy appears on its on-sale date without a re-scrape; the next scrape rewrites the flag anyway. Run records gain `notAtStore` (count) and `alcoholAvailability`.
  **Limits:** (i) past-dated Special Buys that have sold out stay visible (ALDI exposes no stock); (ii) uncategorised alcohol with no spirit word is kept; (iii) a store with no licence at all (`[]`) flags every classified alcohol product but unclassified ones stay; (iv) ALDI's range for a store can still include lines that store happens not to stock, which no API field reveals. **Re-scrape:** needed once to populate the flag (existing rows have none, so nothing is hidden until the next run); dispatch `scrape-fallback.yml` after merge. No other change is needed: API projection already includes `notAtStore` and `onSaleDate`.
